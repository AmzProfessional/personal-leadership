# Створення тестів в amzlms.com

Цей скіл перетворює список питань на реальний тест у LMS: відкриває браузер,
проходить формою створення тесту й додає питання одне за одним.

Головна ідея — **розділити перевірку і виконання**. Помилка у файлі питань
(не позначена правильна відповідь, один варіант замість двох) коштує дешево,
якщо її знайти до відкриття браузера, і дорого, якщо на 34-му питанні в
продакшн-LMS уже лежить наполовину створений тест. Тому спершу завжди йде
`--dry-run`, і лише потім реальний запуск.

## Порядок роботи

### 1. Зібрати питання у файл

Формат — Markdown із frontmatter. Він читабельний для людини, і його легко
редагувати, коли після перевірки треба щось поправити.

```markdown
---
Назва тесту: Персональне лідерство — модуль 1
Опис: Підсумкова перевірка знань за модулем
Категорія: Управління командою
Департаменти: Sales, Support
Прохідний бал: 80
Час: auto
---

## Що таке персональне лідерство?
- [x] Здатність керувати собою та своїми реакціями
- [ ] Здатність контролювати роботу підлеглих
- [ ] Формальна посада в компанії
> Персональне лідерство починається з управління собою.

## Оберіть складові персонального лідерства
type: multiple
- [x] Самосвідомість
- [x] Саморегуляція
- [ ] Мікроменеджмент
> Перші дві — базові складові моделі.
```

Що варто знати про формат:

- `- [x]` — правильна відповідь, `- [ ]` — неправильна. Це єдина розмітка,
  яку треба пам'ятати.
- `type:` можна не писати. Якщо позначено одну правильну відповідь — це
  `single`, якщо кілька — `multiple`. Пиши `type:` явно лише тоді, коли
  питання з кількома варіантами має поки що одну правильну відповідь.
- `>` — пояснення, яке LMS показує після відповіді. Префікс «Пояснення:»
  всередині можна писати або ні, він однаково прибирається.
- `Час: auto` рахує час як **одна хвилина на питання** — це стандарт
  користувача. Можна вказати число, якщо потрібен інший.
- `Прохідний бал` за замовчуванням 80.
- Нумерація в заголовку (`## 3. Питання`) прибирається автоматично, тож
  список питань можна вставляти як є.

Повний опис формату, включно з JSON-варіантом і всіма синонімами полів —
у `references/format.md`. Шаблон для копіювання — `assets/questions.example.md`.

### 2. Перевірити файл, не відкриваючи браузер

```bash
cd .claude/skills/amzlms-test-creator
node scripts/create-test.mjs шлях/до/questions.md --dry-run
```

Виводить план: назву, категорію, порахований час, кількість питань, а також
попередження й помилки. Помилки блокують запуск — це навмисно. Покажи цей
план користувачеві перед реальним запуском, щоб він міг звірити категорію,
департаменти й час.

### 3. Разова калібровка селекторів (тільки перший раз)

Розмітка LMS невідома наперед, і вгадувати її наосліп — найшвидший спосіб
зіпсувати дані. Тому перед першим справжнім запуском:

```bash
node scripts/discover.mjs --stage question
```

Скрипт відкриє браузер, дочекається входу, пройде на форму створення тесту й
збереже `discovery-report.json` — перелік усіх полів і кнопок із готовими CSS-
селекторами, плюс звіт, які з налаштованих полів розпізналися і яким способом.

Прочитай звіт і для всього, що позначене `✗ НЕ ЗНАЙДЕНО` (або знайдено
способом `anchored:` — це найненадійніший шлях), пропиши точний селектор у
`config/selectors.json`. Детальний розбір, як це робити — у
`references/calibration.md`.

### 4. Створити тест

```bash
node scripts/create-test.mjs шлях/до/questions.md
```

Браузер відкривається у видимому режимі навмисно: перший запуск варто
подивитись очима. Прогрес пишеться на диск після кожного збереженого питання,
тож якщо щось зламається на 20-му з 40, решту можна дозалити:

```bash
node scripts/create-test.mjs шлях/до/questions.md --resume
```

При помилці скрипт зберігає знімок екрана і **не закриває браузер** — крок
можна довести руками, а потім продовжити з `--resume`.

## Вхід у LMS

Скіл не працює з паролями. Використовується постійний профіль Chromium у
`~/.amzlms-automation/profile`: перший запуск зупиняється на сторінці входу,
користувач заходить руками, сесія зберігається в профілі й наступні запуски
стартують уже авторизованими.

## Опції

| Опція | Що робить |
| --- | --- |
| `--dry-run` | Тільки перевірка файлу і план. Браузер не відкривається. |
| `--resume` | Продовжити з питання, наступного за останнім збереженим. |
| `--start-at N` | Почати з питання N, ігноруючи збережений прогрес. |
| `--headless` | Без вікна. Тільки якщо вхід у LMS уже виконувався раніше. |
| `--slow-mo MS` | Затримка між діями (за замовчуванням 40 мс). |
| `--base-url URL` | Інша сторінка бази знань. |
| `--config PATH` | Інший файл селекторів. |
| `--keep-open` | Не закривати браузер після завершення. |

## Перед першим використанням

```bash
cd .claude/skills/amzlms-test-creator
npm run setup     # npm install + завантаження Chromium
```

## Перевірка після змін у скрипті

Є mock-LMS, який повторює форми справжньої (кастомні дропдауни, модалка
питання, рядки відповідей, що додаються динамічно). Він дозволяє перевірити
автоматизацію, нічого не записуючи в продакшн:

```bash
npm test
```

Якщо правиш `scripts/dom.mjs` або `scripts/create-test.mjs` — прожени тести.
Особливо це стосується логіки пошуку полів: там легко зробити так, що поле
«знайдеться», але не те, і текст категорії поїде в назву тесту.

## Що робити, коли щось не працює

`references/troubleshooting.md` — типові збої та їх причини: поле не
знайдено, дропдаун не відкривається, не вистачає рядків відповідей, питання
зберігається порожнім.

## Межі скіла

- Скіл **створює** тести й питання. Він не публікує їх і не призначає
  користувачам — це свідомо залишено людині, бо публікація розсилає тест
  співробітникам.
- Питання додаються по одному через інтерфейс. Для сотень питань це довго;
  якщо це стане проблемою, у `references/troubleshooting.md` описано, як
  подивитися мережеві запити LMS і чи є придатний API.
- Скіл не редагує наявні питання й нічого не видаляє.
